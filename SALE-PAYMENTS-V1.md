# Sale Payments V1

## Implementation

Confirmed sales now accept immutable customer payment records. `/sales` displays Total, Payé, Reste, and Paiement separately from Statut vente. Sale details show Total vente, Total payé, Reste à payer, the payment badge, and newest-first history with date/amount/method/reference/notes.

`/sales/[id]/payments/new` provides the payment form and current balance summary. The add-payment action is only available for confirmed sales with a positive balance. DRAFT/CANCELLED/fully paid sales show an explanatory message on direct form navigation. The form validates positive exact amounts, the loaded balance, method, and date, disables submission while pending, preserves errors, and redirects to fresh sale details after success. Cancellation returns to details.

The UI reuses existing payment labels/badges, decimal normalization/comparison, money formatting, and dashboard styles. Arabic references/notes use UTF-8 and automatic text direction. No dependencies were installed. Payment editing/deletion, CashMovement, caisse, ecommerce checkout, and accounting were not added.

## Database changes

Added only `public.salePayment`:

| Field | Storage / constraints |
| --- | --- |
| id | SERIAL primary key |
| saleId | Required int4 FK to Sale.id; RESTRICT on delete/update |
| amount | Required numeric; CHECK positive and finite |
| paymentMethod | Required text; CHECK CASH / CARD / BANK_TRANSFER / CHECK / OTHER |
| paymentDate | Required ISO YYYY-MM-DD text, calendar-validated by the backend |
| reference | Nullable informational text, not unique |
| notes | Nullable text |
| createdAt | Required timestamptz, default now() |

Indexes: saleId and saleId + paymentDate. The standalone FK index is generated by Prisma. The owning-side relation derives the inverse Sale relation. No stored/editable totalPaid, remainingAmount, or paymentStatus columns were added. Existing table fields remain unchanged.

Contract emit and dry-run completed; the migration was reviewed and safely applied. `20260906T1743_sale_payments_v1` has four additive operations: table with checks, two indexes, and FK. Its generated operations getter uses the explicit return type required by the full TypeScript check.

## API and validation

| Endpoint | Behavior |
| --- | --- |
| POST /sales/:id/payments | 201, creates and returns one SalePayment |
| GET /sales/:id/payments | 200, history ordered by paymentDate descending then id descending |

Existing sale responses now include totalPaid, remainingAmount, paymentStatus, and payments in addition to the existing line-derived totalAmount. Read transactions provide consistent summaries/history.

Validation reuses the purchase-payment input rules through a sale DTO export: amount must be a positive decimal string, method must be supported, date must be a real calendar date, optional reference/notes must be text or null, and unknown fields are rejected. Blank optional text becomes null. Invalid input returns 400. Missing sales return 404. Non-confirmed sales and amounts exceeding the remaining balance return clear 409 errors. Fully paid sales reject every additional positive payment.

## Balances and exact arithmetic

- totalAmount = sum of SaleLine.lineTotal.
- totalPaid = sum of SalePayment.amount.
- remainingAmount = totalAmount − totalPaid.
- NON_PAID → Non payé when totalPaid = 0.
- PARTIALLY_PAID → Partiellement payé when 0 < totalPaid < totalAmount.
- PAID → Payé when totalPaid = totalAmount.

The existing BigInt money helpers use a fixed scale of 36 fractional digits, matching sale-total precision. Amount inputs allow up to 130 integer digits and 36 fractional digits. Values are never rounded or converted through binary floating-point amounts. The frontend keeps decimal strings and compares them exactly; display uses grouped digits, a comma, and DT, retaining extra precision beyond three decimals. Tests cover 0.1 + 0.2 and settlement of a total at the 36th decimal place.

## Concurrency and business integrity

Each payment transaction uses the existing dedicated PostgreSQL connection and Prisma transaction-scoped ORM. It locks the sale row FOR UPDATE, verifies CONFIRMED, reads sale lines and payments, derives the current balance, validates the new amount, inserts one SalePayment, and commits. A concurrent payment waits for the same row lock and rechecks against committed payments afterward. Two 80 payments against 100 remaining therefore yield one success and one conflict.

The same sale lock is used by confirmation/editing. Recording a payment does not update Sale (including its timestamps), SaleLine, Product, or StockMovement. No new stock movement is generated. The API has no payment update/delete endpoints; history is immutable through the application.

SalePayment records how a customer paid a particular sale. A future CashMovement would represent a movement in a cash-register context. They are separate concepts: this implementation neither creates a register nor maps every payment method to cash. Payment creation is isolated in one service method/transaction so future explicitly requested cash linkage can be added coherently without changing stock confirmation.

V1 does not implement idempotency keys. Reference is informational, not a unique retry key. The UI prevents duplicate clicks while pending; after an uncertain network result, inspect history before retrying. Separate accepted requests can record separate payments when sufficient balance remains, but cannot overpay through this API.

## Exact manual test steps

1. Start backend with `npm.cmd run start:dev` in `C:\herb-store-system\backend`, and frontend with `npm.cmd run dev` in `C:\herb-store-system\frontend`, unless already running. The migration is already applied.
2. Use a disposable product with enough stock and create a draft sale totaling 50.000 DT. On details verify Non payé and no payment action. Direct `/sales/<id>/payments/new` should explain that only confirmed sales accept payments.
3. Confirm that disposable sale. Record the sale total and resulting stock. Details should show Total vente 50,000 DT, Total payé 0,000 DT, Reste à payer 50,000 DT, and Ajouter un paiement.
4. Open the payment form. Verify all five methods and required fields. Try blank, zero, negative, or 51 as amount: submission must be blocked. Annuler must return without creating a payment.
5. Record 20,000 DT with Espèces, a date, and Arabic reference/notes. Expect Enregistrement..., then return to details with Partiellement payé, paid 20,000 DT, remaining 30,000 DT, and one history row.
6. Check `/sales`: the sale status remains Confirmée, separately from payment status. The sale total and stock must be unchanged by the payment.
7. Try paying 40,000 DT: reject as exceeding the remaining 30,000. Then record exactly 30,000 DT, using Carte or Virement bancaire and a later date. Expect Payé, zero remaining, newest-first history, and no add-payment action. Direct form navigation must show that the sale is fully paid.
8. On another disposable confirmed sale with 100 remaining, open two payment forms in separate tabs. Submit 80 from both: one succeeds and one receives a balance conflict. Reload details: paid 80,000 DT, remaining 20,000 DT, one payment.
9. Test a disposable sale totaling 0,300 DT with payments 0,100 and 0,200. It must settle with exactly zero remaining.
10. Check empty history, nonexistent ID 2147483647, temporary backend failure, keyboard navigation, mobile table scrolling, Arabic text, and DT formatting. Failed requests must show errors and retain form inputs. After an uncertain request result, inspect history before resubmitting.

Payments are intentionally not editable/deletable in V1. Use disposable sales for these manual checks; do not enter test payments against genuine balances.
