# Purchase Payments V1

## Implementation

Confirmed purchases now support independent payment records. The purchase list shows Total, Payé, Reste, and a payment badge separately from purchase status. Details show a payment summary and newest-first history. The new route `/purchases/[id]/payments/new` provides amount, method, date, optional reference, and notes, with validation, loading/submitting/error states and cancellation back to details.

The add-payment action appears only for CONFIRMED purchases with a positive remaining balance. Direct navigation to the form for DRAFT, CANCELLED, or fully paid purchases shows an explanatory message instead of payment fields. Successful saves reload purchase details and its authoritative summary/history. Arabic text uses UTF-8 and automatic direction. Monetary values retain exact precision and display grouped digits with a comma, for example `1 500,000 DT`.

Payments are immutable through the API/UI: no edit/delete endpoints or controls. No sales, accounting ledger, cash register, or external money-transfer integration was added. Purchase confirmation and stock business rules are unchanged.

## Database changes

Added only `public.purchasePayment`:

| Field | Storage / constraints |
| --- | --- |
| id | SERIAL primary key |
| purchaseId | Required int4, FK to Purchase.id, RESTRICT on delete/update |
| amount | Required numeric, CHECK positive and finite |
| paymentMethod | Required text, CHECK CASH / BANK_TRANSFER / CARD / CHECK / OTHER |
| paymentDate | Required ISO date text YYYY-MM-DD, calendar-validated by the backend |
| reference | Nullable text, informational and not unique |
| notes | Nullable text |
| createdAt | Required timestamptz, default now() |

Indexes: purchaseId and purchaseId + paymentDate (the single-column FK index is generated by Prisma). The relation is declared on PurchasePayment; Prisma derives the inverse relation. No editable/stored totalPaid, remainingAmount, or paymentStatus columns were added. No existing model columns were changed.

The contract was emitted and the database dry-run reviewed. Migration `20260906T1319_purchase_payments_v1` was applied safely: four additive operations, consisting of the table with checks, two indexes, and one FK. Its generated operations getter uses the project's explicit return-type pattern for full TypeScript checking.

## API

| Endpoint | Behavior |
| --- | --- |
| POST /purchases/:id/payments | Creates a payment and returns the payment record, HTTP 201 |
| GET /purchases/:id/payments | Returns payment history, HTTP 200; missing purchase returns 404 |

All existing purchase responses now also contain totalPaid, remainingAmount, paymentStatus, and a payments array. The existing totalAmount remains derived exclusively from PurchaseLine.lineTotal. History sorts by paymentDate descending, then id descending for same-date entries.

Validation rejects malformed/unknown fields, missing or invalid decimal amounts, zero/negative amounts, unsupported methods, invalid calendar dates, and non-text optional fields. Optional blank text becomes null. A missing purchase returns 404. DRAFT/CANCELLED purchases and amounts exceeding the current remaining balance return clear HTTP 409 errors. Invalid input returns HTTP 400. Payment is allowed for an existing confirmed purchase even if its supplier was later deactivated; historical supplier obligations remain payable.

## Derived balances and exact arithmetic

- totalAmount = sum of purchase lineTotal values.
- totalPaid = sum of independent payment amounts.
- remainingAmount = totalAmount − totalPaid.
- NON_PAID / Non payé: totalPaid = 0.
- PARTIALLY_PAID / Partiellement payé: 0 < totalPaid < totalAmount.
- PAID / Payé: totalPaid = totalAmount.

Backend arithmetic uses scaled BigInt integers at 36 decimal places, matching the full precision of existing purchase line totals. Payment amounts are decimal strings supporting up to 130 integer digits and 36 fractional digits. No rounding or binary floating-point arithmetic is used. At least three fractional digits are returned/displayed, with additional exact precision retained. This permits exact settlement even for a purchase total of 0.000000000000000000000000000000000001 DT.

The frontend normalizes comma/dot input, retains decimal strings, and compares the amount with the loaded remaining balance using the existing string decimal comparator. Backend validation rechecks the current balance at submission. Derived amounts are never accepted from the client or written onto the purchase.

## Concurrency and immutability

Payment creation uses the existing dedicated-connection, Prisma-managed purchase transaction. It locks the purchase row FOR UPDATE, verifies CONFIRMED, reads the line total and committed payment history, checks the remaining balance, and inserts the payment before committing. A concurrent payment waits for that row lock, then calculates against the updated balance. Two payments of 80 against a remaining 100 therefore produce one success and one conflict.

This is also the lock used by purchase confirmation/editing. The transaction-scoped ORM is retained so no nested root-ORM mutation can commit independently. Payment insertion does not update Purchase, PurchaseLine, Product, or StockMovement. List/details/history reads retain consistent transactional snapshots.

There is no request idempotency key in V1. A payment reference is informational, not a deduplication key. The UI guards double submission while a request is pending; after an uncertain network result, inspect history before retrying. Separate accepted requests can record separate payments if sufficient balance remains, but cannot overpay through this API.

## Exact manual test steps

1. Start backend with `npm.cmd run start:dev` in `C:\herb-store-system\backend` and frontend with `npm.cmd run dev` in `C:\herb-store-system\frontend`, unless already running. The payment migration is already applied.
2. Use a disposable supplier/product and create a purchase with total 100.000 DT. While DRAFT, verify details show Non payé and no add-payment control. Direct navigation to `/purchases/<id>/payments/new` must explain that only confirmed purchases can receive payments.
3. Confirm the disposable purchase. Record its current stock and total. Details should show Total achat 100,000 DT, Total payé 0,000 DT, Reste à payer 100,000 DT, and “Ajouter un paiement”.
4. Click the button. Verify the summary, all five method labels, and required amount/method/date. Try empty, zero, negative, or 101 as amount: validation must prevent submission. Annuler returns to details without recording anything.
5. Enter 40,000, select Espèces, choose a date, and enter an Arabic reference/notes. Save. Expect “Enregistrement...”, then return to details with Partiellement payé, paid 40,000 DT, remaining 60,000 DT, and one history row.
6. Check `/purchases`: purchase status remains Confirmé while payment status is Partiellement payé. Total is still 100,000 DT. Check `/stock`: payment creation must not affect stock.
7. Add the exact remainder, 60,000 DT, using Virement bancaire and a newer payment date. Expect Payé, remaining 0,000 DT, two newest-first history rows, and no add-payment button. Direct navigation to the form should show that the purchase is fully paid.
8. For a concurrency check, use another disposable confirmed purchase with 100 remaining. Open its payment form in two tabs, enter 80 in each, and submit both. Exactly one may succeed; the other must show a balance error. Reload details and verify paid 80,000 DT and remaining 20,000 DT.
9. Test a 0,300 DT disposable purchase with payments 0,100 and 0,200: it must settle exactly with no tiny residual balance.
10. Temporarily stop the backend to inspect loading/save errors, then restart it. After a request with uncertain outcome, inspect payment history before resubmitting. Test a narrow viewport, table scrolling, keyboard navigation, grouped DT values, and Arabic text.

Manual payment records intentionally have no edit/delete UI. Keep these tests on disposable purchases; do not record test payments against genuine supplier balances.
