# Stock history, alerts, and dashboard

## Implementation

Frontend-only change. No backend endpoints, business rules, schema, write behavior, or dependencies were changed. Existing movement forms and product restrictions remain in place. No movement edit/delete controls or editable stock quantity were added.

Routes:

- `/stock`: summary cards, all six movement actions, Historique link, stock search/status filter, alert-priority ordering, and product detail links.
- `/stock/movements`: immutable movement history with date, product, SKU, French movement type, quantity, unit, converted quantity plus storage unit, reason, and reference.
- `/stock/products/[id]`: product name, SKU, category, backend stock, unit, minimum/maximum thresholds, location, status, and the latest 20 movements, newest first.

Existing APIs used: GET `/products`, `/products/:id`, `/products/:id/stock`, and `/stock-movements`. API loading, runtime response validation, view calculations, and rendering are separated for future backend filtering or bulk balance endpoints.

## Summary and alert definitions

Balances come only from GET `/products/:id/stock`. Decimal text comparison avoids floating-point rounding.

- Rupture: current stock equals zero, including when the minimum is null or zero.
- Stock faible: stock is positive, minimum is defined, and stock is less than or equal to minimum.
- Normal: otherwise.

Dashboard cards count all loaded products, independent of search/status filters. The low-stock count excludes ruptures.

Recent movements means the inclusive interval `[load completion time - 168 hours, load completion time]`, across all products and all six movement types. Future-dated movements are excluded. The load time is displayed; Actualiser reloads the data and advances the reference time. This is a rolling seven-day window, not seven calendar dates.

Rows sort by Rupture, Stock faible, Normal, then French-locale alphabetical product name and SKU. Search matches product name, French name, or SKU, supports Arabic, and is case-insensitive. Status and search filters combine. Reset clears both.

## History filters

Product, movement type, start date, and end date combine using AND. Date filters use the browser's local timezone: start midnight is inclusive, and midnight after the end date is exclusive, so the whole selected end date is included. An inverted date range shows an error and no matching rows. Reset clears all filters.

Timestamps returned in PostgreSQL's space-separated format and short offset are normalized before parsing. Dates are displayed in French, in the browser's local timezone. History sorts newest first, with movement ID as a tie-breaker. Positive/negative movement badges have distinct colors and text labels; stored quantities are displayed unchanged, without recalculating stock or conversions.

## Manual checks

1. Open http://localhost:3000/stock with both servers running. Verify the four summary cards, timestamp, six movement actions, and Historique link.
2. Search an existing product by SKU, Arabic name, or French name. Combine with each status filter and reset. Cards must remain totals for the whole catalog.
3. Confirm zero stock sorts first as Rupture; positive stock at/below minimum sorts next as Stock faible; other products show Normal. The automated helper checks cover these cases without changing real data.
4. Click Historique. Check French labels, positive/negative badges, original quantities, backend-converted quantities, dates, reason, and reference.
5. Filter by a product and movement type together. Select a date containing an existing movement as both start and end; that movement should remain visible. Try an inverted range, a range with no matches, then Réinitialiser les filtres.
6. Click Détails in the dashboard or a product name in history. Verify all product stock fields, status, and its latest 20 movements. Actualiser reloads them.
7. Use network throttling to inspect loading. Stop the backend before refreshing to inspect errors; restart and use Réessayer. Empty histories show exactly `Aucun mouvement de stock`.
8. Check narrow screens for horizontal table scrolling, keyboard access to controls, and Arabic names without garbled text. Confirm all existing movement-form links remain available.

## Limitations

No remaining blocker. Interactive browser filtering was not automated; pure filter logic and HTTP routes were tested.

Filtering uses the currently loaded dataset. Balances are fetched in batches of six using the existing per-product endpoint; history is fetched in full. These choices fit the current small dataset and avoid backend changes. For a larger catalog, add a paginated history endpoint and bulk stock reads. The separate requests are not an atomic cross-product database snapshot; Actualiser obtains fresh values after concurrent changes. The product detail view fetches full history and selects its product locally.
